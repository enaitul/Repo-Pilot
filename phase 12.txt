==============================================================================
1. WHAT IS PHASE 12?
==============================================================================

Phase 12 connects RepoPilot's existing code understanding, automated modification,
safety validation, test execution, and code review capabilities directly to
a controlled GitHub developer workflow.

The full name is:

    GITHUB DEVELOPER WORKFLOW INTEGRATION

Think of it this way:

- Phase 1 to 8 built RepoPilot's "Brain" (understanding and analyzing code).
- Phase 10 built RepoPilot's "Hands" (making controlled edits to local files).
- Phase 11 built RepoPilot's "Eyes" (reviewing code for bugs and quality).
- Phase 12 builds RepoPilot's "Bridge to GitHub" (connecting those local capabilities
  to remote GitHub repositories, branches, and pull requests in a safe, controlled way).

Before Phase 12, RepoPilot only clones a public GitHub repository locally, analyzes
it, modifies local temporary files, runs local tests, and generates a local code review.
Phase 12 provides a clean bridge so that a developer can seamlessly review those
changes and publish them back to GitHub as feature branches or Pull Requests without
manually copying files between systems.


==============================================================================
2. WHY DO WE NEED PHASE 12?
==============================================================================

After Phase 11, RepoPilot can clone a repository, understand its structure, answer
questions, plan changes, apply modifications, run tests, and perform a deep code review.

However, there is a disconnect between RepoPilot and real-world developer workflows:

1. MANUAL ISOLATION:
   Currently, RepoPilot operates on a local temporary folder (created via `tempfile.mkdtemp()`).
   Once RepoPilot finishes making edits and reviewing them, those changes stay in that
   temporary directory. A developer would have to manually open that folder, copy the files,
   create a Git branch, write a commit message, and open a Pull Request manually.

2. READ-ONLY GITHUB INTERACTION:
   RepoPilot's interaction with GitHub is strictly read-only cloning. It has no way to
   communicate back to GitHub (such as pushing a branch or opening a Pull Request).

3. WORKFLOW FRICTION:
   In modern software engineering, developers work using Git branches, Pull Requests (PRs),
   and code reviews on platforms like GitHub. Without Phase 12, RepoPilot is an isolated
   tool rather than a natural part of the developer workflow.

Phase 12 solves these problems by creating a controlled, human-in-the-loop workflow
between local RepoPilot execution and GitHub.

3. WHAT CAN REPOPILOT DO AFTER PHASE 11?
==============================================================================

Here is what RepoPilot can do today, based on the actual codebase:

PHASE 1/2 — Repository Ingestion (IngestionService & GitCloner)
    Validate public GitHub HTTPS URLs (`validate_repo_url()`).
    Shallow-clone a repository into an isolated temporary folder (`GitCloner.clone()`).
    Walk the filesystem (`RepoWalker`) and detect languages (`language_detector.py`).
    Build a `RepositoryModel` with file metadata (`FileMetadata`).

PHASE 3 — Code Parsing (ParsingService)
    Parse Python files using the standard `ast` module (`python_parser.py`).
    Parse multi-language source files using Tree-sitter (`treesitter_parser.py`).
    Extract structured `CodeSymbol` objects (classes, functions, methods with line bounds).

PHASE 4 — Code Chunking (ChunkingService)
    Break file symbols into logical `CodeChunk` objects with line bounds and context.
    Apply sliding-window splitting with overlapping lines for large symbols.

PHASE 5 — Embeddings (EmbeddingService)
    Convert code chunks into numerical vector representations using sentence-transformers
    (`all-MiniLM-L6-v2`).

PHASE 6 — Vector Database & Semantic Retrieval (VectorStore & SearchService)
    Store vectors in a FAISS vector index with L2/Cosine normalization.
    Perform similarity search to retrieve relevant code chunks for user queries.

PHASE 7 — RAG Pipeline (RAGService)
    Retrieve code context, build grounded prompts (`PromptBuilder`), and generate answers
    using Groq LLM (`llama-3.3-70b-versatile`).

PHASE 8 — Repository Intelligence (RepositoryIntelligenceService)
    Analyze tech stacks (`TechnologyDetector`), key files (`ImportantFileDetector`),
    entry points, and import-based dependency graphs (`DependencyGraphBuilder`).

PHASE 9 — Intelligent Developer Actions (ActionService)
    Execute structured requests: `TEST_GENERATION`, `DOCUMENTATION`, `REFACTORING`,
    `BUG_ANALYSIS`, and `CHANGE_PLAN`.

PHASE 10 — Controlled Code Modification (ModificationService)
    Apply structured changes (create, replace, delete) inside a workspace copy (`WorkspaceTools`).
    Validate syntax with `compile()` (`ValidationService`).
    Run isolated `pytest` test suites (`TestRunner`).
    Roll back workspace edits automatically if tests fail.

PHASE 11 — Intelligent Code Review (ReviewService)
    Analyze code diffs (`FileDiff`) and whole files against 5 review categories
    (Bug Risk, Security, Performance, Maintainability, Architecture).
    Generate evidence-grounded findings (`ReviewFinding`) ranked by severity.
    Produce structured review reports (`ReviewReport`).

6. WHAT IS GITHUB INTEGRATION?
==============================================================================

Let's break down the technical terms for a student:

1. Technical Term: GitHub Integration
   Simple Explanation: Connecting a local software tool to GitHub's online service so
   the tool can read from or write to GitHub repositories on your behalf.
   Small Example: When you log into VS Code and click "Publish to GitHub", VS Code is using
   GitHub integration to create a remote repository and upload your files.

2. Technical Term: Remote Repository
   Simple Explanation: The copy of a project's codebase hosted on GitHub's servers, which
   serves as the central source of truth for a development team.
   Small Example: `https://github.com/torvalds/linux` is a remote repository on GitHub.

3. Technical Term: Developer Workflow
   Simple Explanation: The sequence of steps a programmer follows to write code, test it,
   review it, and publish it into a shared codebase.
   Small Example: Pull latest code -> Create branch -> Write feature -> Run tests ->
   Push branch -> Open Pull Request -> Merge code.

Without GitHub integration, RepoPilot is like a brilliant assistant working on a desktop

  results, and review notes directly on GitHub in a familiar PR format.
- Safety & Traceability: Every AI-generated change is isolated in its own branch, tagged with
  a clear commit author/message, and subject to human approval.

commits the changes, and pushes the branch to GitHub.

and Phase 11 review findings.

9. GITHUB REPOSITORY ACCESS
==============================================================================

Let's examine how RepoPilot currently handles GitHub repositories in the actual codebase vs
what Phase 12 proposes.

CURRENTLY IMPLEMENTED (Source of Truth in `cloner.py`):

1. Repository URL Handling:
   - Function: `validate_repo_url(url: str)` in `repopilot/cloner.py`.
   - Strict Regex Validation: Matches `^https://github\.com/[\w.\-]+/[\w.\-]+(?:\.git)?/?$`.
   - Rejects non-GitHub URLs, SSH URLs (`git@github.com:...`), file paths (`file://`), and plain HTTP.
   - Appends `.git` normalization if missing.

2. Repository Cloning:
   - Class: `GitCloner` in `repopilot/cloner.py`.
   - Shallow Clone: Executes `git clone --depth 1 --single-branch <url> <temp_dir>`.
   - Temporary Directory: Uses Python's `tempfile.mkdtemp(prefix="repopilot_")`.
   - Execution Safety: Invokes subprocess with a list of arguments (`subprocess.run(["git", "clone", ...])`). Never uses `shell=True`, preventing command injection attacks.
   - Timeout: Enforces `CLONE_TIMEOUT_SECONDS = 120`.

3. Authentication:
   - CURRENTLY NONE. The existing codebase only supports public GitHub repositories over HTTPS without authentication headers or tokens.

4. Private Repository Support:
   - CURRENTLY NOT SUPPORTED. Attempting to clone a private repository URL currently fails with a `CloneError` because git cannot authenticate.

PROPOSED FOR PHASE 12:

1. Private Repository Support:
   - Support private GitHub repositories by passing authentication tokens securely to Git CLI or GitHub API requests.

2. Credential Handling:
   - Credentials must NEVER be hardcoded, logged to disk, or stored in temporary files.
   - Store credentials in environment variables (e.g., `GITHUB_TOKEN`) or OS keyrings.
   - Pass tokens to Git commands using authenticated HTTPS URLs (e.g., `https://x-access-token:<token>@github.com/owner/repo.git`) or Git credential helpers in memory only.

10. AUTHENTICATION
==============================================================================

What is GitHub Authentication?
Authentication is how a software system proves its identity to GitHub so GitHub knows
who is making requests and what repositories they are allowed to access.

Key Authentication Concepts:

1. Personal Access Token (PAT)
   - What it is: A password-like string generated by a user in GitHub settings.
   - Simple Example: `ghp_1234567890abcdefghijklmnopqrstuvwxyz`
   - Tradeoff: Simple to configure for personal projects, but tied to an individual user's account and can be over-permissioned if created carelessly.

2. OAuth (Open Authorization)
   - What it is: A secure login standard that allows users to grant RepoPilot access to their GitHub account without sharing their GitHub password.
   - Simple Example: Clicking "Sign in with GitHub" on a web app and authorizing permissions.
   - Tradeoff: Great user experience for web applications, but requires managing redirect servers and OAuth application credentials.

3. GitHub App
   - What it is: A specialized bot account registered directly on GitHub that can be installed on specific repositories.
   - Simple Example: Dependabot or Renovate bot on GitHub.
   - Tradeoff: Most secure and granular for organization-level workflows, but requires more initial setup (App ID, Private Keys, Installations).

Token Security & Storage Best Practices:
- Always load tokens from standard environment variables (e.g., `GITHUB_TOKEN`).
- Scrub tokens from all log messages, exception tracebacks, and terminal outputs.
- Never store tokens in the git repository or disk cache files (`.faiss` or `metadata.json`).

11. PERMISSIONS
==============================================================================

What are GitHub Permissions?
Permissions define the specific actions RepoPilot is allowed to perform on a GitHub repository.

The Principle of Least Privilege:
A fundamental security principle stating that a system should only be given the absolute
minimum access rights necessary to complete its assigned job, and no more.

Why RepoPilot Should Use Minimum Required Permissions:

If RepoPilot only needs to read code, create a branch, and open a PR, it should NEVER be
given full admin rights, delete permissions, or repository setting access.

Required Permission Granularity for Phase 12:

1. `contents: read` — Required to clone and read repository code.
2. `contents: write` — Required to push a new feature branch to GitHub.
3. `pull_requests: write` — Required to open a Pull Request on GitHub.
4. `issues: read` — Optional for fetching bug reports (postponed).

Permissions to Exclude / Block:
- NO admin rights (`admin: repo_hook` or `delete_repo`).
- NO workflow modification permissions (`workflows: write`).
- NO permission to push directly to protected main branches (`main` / `master`).

12. BRANCHES
==============================================================================

What is a Git Branch?
A branch is an isolated workspace within Git that splits off from the main codebase. It allows
you to make and test changes without affecting the working code used by other developers.

Simple Example:
Imagine writing a book. The `main` branch is the published edition. A `feature` branch is
a working draft notebook where you write new chapters. You don't paste your rough drafts into
the published edition until they are reviewed and edited.

The Proposed Git Branching Model for RepoPilot:

    [ main branch ] (Protected, central production code)
          │
          ├───► [ feature/repopilot-fix-auth ] (Isolated branch created by RepoPilot)
                      │
                      ├── Apply Phase 10 modifications
                      ├── Run Phase 10 unit tests
                      ├── Perform Phase 11 code review
                      │
                      ▼
          [ Push branch to GitHub & Open Pull Request ]

Why Modifying the Default `main` Branch Directly is Dangerous:
1. Broken Production Code: If AI-generated code has an unexpected bug, pushing directly to
   `main` immediately breaks the project for everyone on the team.
2. No Peer Review: Directly editing `main` bypasses GitHub code reviews and CI/CD pipelines.
3. Difficult Rollbacks: Reverting bad commits on `main` causes messy Git history and conflict
   headaches for team members.

How Feature Branches Act as a Safety Boundary:
Feature branches guarantee that all RepoPilot modifications exist in complete isolation until
a human developer reviews and approves merging them into `main`.

16. GITHUB API
==============================================================================

What is the GitHub API?
The GitHub API (Application Programming Interface) is an HTTP-based service provided by
GitHub that lets software programs interact programmatically with GitHub resources (such as
repositories, issues, branches, and pull requests) over the internet.

GitHub API Operations Overview:

Operations Needed for Phase 12:
1. `GET /repos/{owner}/{repo}` — Check repository details and verify access.
2. `POST /repos/{owner}/{repo}/git/refs` — Create a new remote branch reference.
3. `POST /repos/{owner}/{repo}/pulls` — Create a Pull Request.
4. `GET /repos/{owner}/{repo}/pulls/{pull_number}` — Check status of an existing PR.

Postponed Operations (Phase 13+ / Out of Scope):
- `POST /repos/{owner}/{repo}/issues/{issue_number}/comments` — Post issue comments.
- `PUT /repos/{owner}/{repo}/pulls/{pull_number}/merge` — Merge pull requests automatically.
- `DELETE /repos/{owner}/{repo}/git/refs/heads/{branch}` — Delete remote branches.
- Workflow trigger APIs (`POST /repos/{owner}/{repo}/actions/workflows/...`).

17. GIT OPERATIONS
==============================================================================

Difference Between Git and GitHub:

- Git: A local, open-source distributed version control command-line tool that runs on
  your computer to track code file changes over time.
- GitHub: A cloud-based hosting platform service that stores Git repositories online and
  provides web UIs, permissions, issue tracking, and pull request features.

Core Git Operations & How They Connect to RepoPilot:

1. Clone (`git clone`)
   - What it does: Downloads a remote repository from GitHub onto local disk.
   - Connection: Currently implemented in Phase 1 (`GitCloner.clone()`).

2. Branch (`git branch` / `git checkout -b`)
   - What it does: Creates and switches to a new isolated line of development.
   - Connection: Proposed for Phase 12 to isolate AI edits before committing.

3. Commit (`git commit`)
   - What it does: Saves a snapshot of staged changes into the local Git history with a descriptive message.
   - Connection: Proposed for Phase 12 to package Phase 10 edits cleanly.

4. Push (`git push`)
   - What it does: Uploads local branch commits to the remote repository on GitHub.
   - Connection: Proposed for Phase 12 after human developer approval.

5. Pull (`git pull`)
   - What it does: Fetches and merges updates from remote GitHub into local branch.
   - Connection: Used to update local workspace before planning changes.

6. Pull Request (PR)
   - What it does: GitHub web concept (not a Git CLI command) requesting review to merge a branch into `main`.
   - Connection: Proposed Phase 12 output.

18. SECURITY
==============================================================================

Security Risks of GitHub Integration:

Connecting an AI agent tool to remote code repositories introduces key security risks:

1. Token Exposure: Leaking Personal Access Tokens in log files, terminal outputs, or Git commits.
2. Excessive Permissions: Running with write/admin permissions allows compromised scripts to delete repos or alter settings.
3. Untrusted Code Execution: Automatically executing build scripts or test suites from untrusted GitHub repositories.
4. Protected Branch Overwrite: Accidentally force-pushing AI edits directly to `main`, breaking production.
5. Arbitrary Command Execution: Malicious repositories containing engineered configuration files designed to exploit subprocess calls.
6. Secret Leakage: Pushing local `.env` files or API keys into public GitHub commits.

How RepoPilot Reduces Security Risks:
- Enforce strict input validation (`validate_repo_url()` already in place).
- Use list-style `subprocess.run()` without `shell=True` to prevent command injection.
- Enforce Least Privilege (read-only token by default; write scope only when creating PRs).
- Run test suites in isolated workspace environments with execution timeouts.
- Require Human Approval before any git push or PR creation operation.
- Implement file exclusion masks (`.env`, `*.pem`, `id_rsa`) to prevent committing credentials.

Disclaimer: Security risk can be significantly mitigated through defensive design, but can never be guaranteed to be zero.


==============================================================================
19. UNTRUSTED REPOSITORIES
==============================================================================

Why Every GitHub Repository Must Be Treated as Untrusted Input:

In security engineering, any data or repository originating from an external source (such as
a public GitHub URL) must be assumed to be untrusted and potentially hostile.

Potential Threats inside Untrusted Repositories:
- Malicious Test Scripts: A custom test file (`test_setup.py`) that contains code to delete local files or steal environment variables.
- Malicious Package Configurations: Dependency config files (`setup.py`, `package.json`) with pre-install scripts (`postinstall`) that execute arbitrary shell commands.
- Symlink Traversal Attacks: Symlinks pointing outside the repository directory (`/etc/passwd`).
- Resource Exhaustion: Huge binary files or circular directory structures designed to fill disk space.

Safety Rule for RepoPilot:
Cloning a repository means downloading files to disk. It DOES NOT mean RepoPilot should
blindly execute arbitrary setup scripts, shell scripts, or unknown binaries contained
inside that repository. Test execution must remain restricted to safe test runners (such as `pytest`)
with strict timeouts.

22. ERROR HANDLING
==============================================================================

Possible GitHub-Related Failures & Safe Handling Strategies:

1. Invalid Repository URL
   - Cause: User submits malformed URL or non-GitHub link.
   - Handling: Handled by `validate_repo_url()` raising `InvalidRepoURLError`.

2. Authentication Failure / Invalid Token
   - Cause: Token expired, invalid, or missing required scopes.
   - Handling: Catch 401 Unauthorized errors from GitHub API; display clear error message without revealing token; abort operation safely.

3. Permission Denied (HTTP 403)
   - Cause: User/Token lacks write permissions on the target repository.
   - Handling: Abort remote push; notify developer that local changes are preserved in local workspace.

4. Branch Conflict / Branch Already Exists
   - Cause: Target feature branch name already exists on remote.
   - Handling: Append timestamp or random hash suffix to branch name (e.g., `feature/repopilot-fix-auth-1726560000`).

5. Protected Branch Rejection
   - Cause: Push rejected because target branch (`main`) is protected.
   - Handling: Catch push error; verify remote push is targeting feature branch instead of `main`.

6. Rate Limit Exceeded (HTTP 429 / 403 Rate Limit)
   - Cause: Too many requests sent to GitHub API in short period.
   - Handling: Read `Retry-After` header; inform user; pause execution or back off gracefully.

7. Network Failure / Connection Timeout
   - Cause: Internet connection dropped during clone, push, or API call.
   - Handling: Timeout handled via `CLONE_TIMEOUT_SECONDS`; clean up temp folder via `GitCloner.cleanup()`.

23. RATE LIMITING
==============================================================================

What is GitHub API Rate Limiting?
GitHub places limit caps on how many API calls a user or application can make within an hour
to prevent server overload and abuse. Unauthenticated requests are limited to 60 per hour,
while authenticated token requests are granted 5,000 per hour.

Rate Limiting Best Practices for RepoPilot:

1. Minimize API Calls: Perform all parsing, chunking, embedding, vector searching, LLM processing, syntax validation, and testing LOCALLY. Only call GitHub API for final branch/PR operations.
2. Cache Repository Metadata: Store repository metadata locally during the session instead of re-querying GitHub.
3. Exponential Backoff: If an API call hits a rate limit, wait exponentially longer before retrying (e.g., wait 2s, then 4s, then 8s).
4. Inspect Rate Limit Headers: Read `X-RateLimit-Remaining` and `X-RateLimit-Reset` HTTP headers returned by GitHub.

29. DESIGN TRADEOFFS
==============================================================================

Here are the key technical design choices and trade-offs for Phase 12:

1. GitHub API vs. Git CLI
   - Git CLI Subprocess:
     - Advantages: Simple, reuses local git executable, handles branch creation/commits easily.
     - Disadvantages: Requires Git executable on PATH; limited access to GitHub-specific metadata.
   - GitHub REST API:
     - Advantages: Direct access to PR creation, issues, metadata, and token permissions.
     - Disadvantages: Requires network API calls, subject to HTTP rate limits and authentication setup.
   - Resolution: Hybrid approach — use Git CLI for local branching/committing, and GitHub REST API for PR creation.

2. Personal Access Token (PAT) vs. GitHub App
   - Personal Access Token (PAT):
     - Advantages: Easy for single users to set up via environment variables.
     - Disadvantages: Tied to user account; broad permissions if not scoped carefully.
   - GitHub App:
     - Advantages: Granular per-repo permissions, bot identity, secure for teams.
     - Disadvantages: Complex initial setup (App ID, private keys, installation IDs).

3. Direct Main Branch Edits vs. Feature Branches
   - Direct Main Branch Edits:
     - Advantages: Zero branching overhead.
     - Disadvantages: EXTREMELY HIGH RISK of breaking production code. Unacceptable.
   - Feature Branches:
     - Advantages: Complete isolation, full safety boundary, enables pull request reviews.
     - Disadvantages: Requires branch creation and cleanup logic.

4. Automatic Push vs. Human Approval
   - Automatic Push:
     - Advantages: Hands-free execution.
     - Disadvantages: High risk of pushing buggy or unverified code remotely. Unacceptable.
   - Human Approval:
     - Advantages: Guarantees developer control, prevents unintended remote pushes.
     - Disadvantages: Requires interactive user prompt.

5. Automatic PR Creation vs. Manual PR Creation
   - Automatic PR Creation:
     - Advantages: Saves developer time in opening PR web form.
     - Disadvantages: May create clutter if developer wanted to make further local edits.
   - Manual PR Creation:
     - Advantages: Developer has total control over PR timing.
     - Disadvantages: Adds manual step for developer.

6. Full Repository Permissions vs. Least Privilege
   - Full Permissions:
     - Advantages: Avoids permission-denied errors.
     - Disadvantages: Major security vulnerability if token is compromised.
   - Least Privilege:
     - Advantages: Restricts access strictly to read/write contents and pull requests.
     - Disadvantages: Requires clear error messaging if user provides token with missing scopes.

7. Always-Online Workflow vs. Controlled Local Workspace
   - Always-Online Workflow:
     - Advantages: Instant sync with remote servers.
     - Disadvantages: Slow network dependencies for every step; risk of partial online state failures.
   - Controlled Local Workspace:
     - Advantages: Fast, isolated execution; tests and reviews run locally before touch remote servers.
     - Disadvantages: Changes stay local until pushed.
