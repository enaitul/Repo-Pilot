SECTION 1: EXECUTIVE SUMMARY & 30-SECOND ELEVATOR PITCH
================================================================================

"RepoPilot is a full-stack, AI-powered developer productivity and repository intelligence
platform. It allows developers to ingest any public GitHub repository, ask code-grounded
questions using Retrieval-Augmented Generation (RAG), automatically map repository
architecture, perform controlled AI code refactorings inside isolated sandboxes with
AST validation and automated unit testing, run severity-ranked code reviews, and automate
GitHub Pull Request creation.

It combines deterministic code analysis (AST parsing, Git commands, syntax checkers) with
stochastic artificial intelligence (Groq LLM) inside a strict Zero-Trust security sandbox."

Key Highlights for Interviewers:
- Pure Python 3.12 micro-architecture with FastAPI.
- 100% Local Embedding & Vector Search (Sentence-Transformers + FAISS) — zero third-party
  vector database costs or data leaks.
- Zero Execution Risk: LLMs generate structured JSON edits, never raw shell commands.
- Automated rollback on syntax or unit test failures.
- Fully containerized with Docker and live deployed on Render.

SECTION 2: THE PROBLEM & WHY REPOPILOT WAS BUILT
================================================================================

The Problem with Traditional LLMs (ChatGPT, Claude) for Codebases:
1. Context Window Limits: You cannot paste an entire 50,000-line repository into a prompt.
2. Lack of Repository Structure Awareness: Standard LLMs don't understand how files import,
   depend on, or call each other across directory trees.
3. Hallucinated Answers & Invalid Syntax: LLMs frequently suggest code with missing imports,
   broken syntax, or non-existent line numbers.
4. Security Risks: Granting an AI agent raw terminal access (e.g. `eval()` or shell execution)
   exposes systems to malicious prompt injections, arbitrary code execution, or accidental file deletion.

How RepoPilot Solves This:
RepoPilot introduces a controlled hybrid approach:
- Deterministic systems handle file safety, AST symbol parsing, vector search, syntax validation,
  git cloning, and test runner execution.
- LLM AI handles intent reasoning, text summarization, refactoring proposals, and code review.
- Security Sandboxing ensures no original codebase is ever modified, no arbitrary shell commands
  run, and broken code is automatically rolled back.

SECTION 3: CORE ARCHITECTURE & END-TO-END WORKFLOW (PHASES 1 TO 12)
================================================================================

RepoPilot is structured into 12 modular execution phases:

Phase 1 & 2: Safe Ingestion & Shallow Cloning
- Validates public `https://github.com/owner/repo` HTTPS URLs via regex.
- Executes safe `git clone --depth 1` (shallow clone) into an ephemeral workspace directory.
- Filters out non-source files, secret keys, oversized binaries, and rejects path traversal (`../`).

Phase 3: Code & Symbol Parsing
- Uses Python's built-in `ast` module (Abstract Syntax Tree) to parse code files.
- Extracts meaningful code symbols (classes, methods, functions, module-level blocks) instead of
  arbitrary line splits.

Phase 4 & 5: Symbol-Aware Chunking & Local Dense Embeddings
- Combines symbol metadata (File path, Symbol Name, Parent class, Language) with source code.
- Passes chunks through `sentence-transformers` (`all-MiniLM-L6-v2`) to produce 384-dimensional
  dense vector embeddings locally on CPU.

Phase 6 & 7: FAISS Vector Indexing & RAG Querying
- Indexes vectors into an in-memory `faiss.IndexFlatL2` vector store.
- When a user asks a question, converts the query to a 384D vector, performs L2 nearest-neighbor
  search to retrieve top k code chunks, and constructs a grounded RAG prompt for Groq LLM (Llama 3.3).
- Returns answers with exact `file_path:start_line-end_line` citations.

Phase 8: Repository Intelligence & Architecture Fact Extraction
- Scans directory structures, imports, and configuration files.
- Builds deterministic architecture facts: languages used, entry points, technology frameworks,
  important core files, and internal dependency edges.

Phase 9: Developer Advisory Actions
- Provides 5 specialized developer actions:
  1. Test Generation (creates unit tests for targeted symbols)
  2. Documentation Generation (generates docstrings/README summaries)
  3. Code Refactoring Proposals
  4. Bug Analysis & Troubleshooting
  5. High-Level Change Planning

Phase 10: Controlled Code Modification & Sandboxed Testing (CRITICAL PHASE)
- Rejects shell commands. Accepts ONLY structured JSON operations: `create`, `replace`, `delete`.
- Applies modifications ONLY in the disposable cloned workspace directory.
- Runs deterministic post-change checks:
  a. Path safety check (must stay inside temp clone directory)
  b. UTF-8 encoding check
  c. Python AST syntax validation (`ast.parse()`)
- Runs allowlisted test runner (`python -m pytest`) with a strict execution timeout.
- Generates real unified git diffs (`git diff`).
- Automatic Rollback: If syntax validation or unit tests fail, RepoPilot automatically restores
  the workspace to its pre-change state and reports the error.

Phase 11: Automated AI Code Review
- Scans whole repository or diffs against 4 categories: Security, Performance, Code Style, Architecture.
- Returns structured, severity-ranked findings: `CRITICAL`, `HIGH`, `MEDIUM`, `LOW`.

Phase 12: Approval-Gated GitHub Workflow
- Creates local git branches and commits changes inside the workspace.
- Requires explicit user approval in the UI.
- Interacts with GitHub REST API using server-side tokens to automatically push branches and open Pull Requests.

FastAPI REST Layer & UI:
- Thin FastAPI adapter in `api.py` serving REST endpoints (`/api/analyze`, `/api/question`, `/api/modify`, etc.).
- Serves a clean, responsive single-page HTML/CSS/JavaScript web interface directly from `/static`.

SECTION 4: DEEP-DIVE CONCEPTS (FOR INTERVIEW QUESTIONS)
================================================================================

1. Retrieval-Augmented Generation (RAG)
   - What it is: A technique where external data (code chunks retrieved from FAISS) is injected
     into the LLM prompt context before generating an answer.
   - Why we use it: Eliminates LLM hallucinations, enables reasoning over private/new codebases
     beyond the model's training cutoff, and provides exact source line citations.

2. AST (Abstract Syntax Tree) Chunking vs. Naive Line Chunking
   - Naive Chunking: Splitting code every 500 characters or 50 lines often cuts functions in half,
     separating function signatures from their body or docstrings.
   - AST Chunking: Parses Python source code into syntax trees, identifying exact boundary boxes for
     classes, methods, and functions. Every chunk represents a complete logical code unit.

3. FAISS (Facebook AI Similarity Search) & Vector Embeddings
   - Embedding: Mapping text into a 384-dimensional floating-point vector space where semantically
     similar code snippets are close to each other.
   - Vector Search: FAISS uses L2 Euclidean distance math to find the top matching code chunks in
     milliseconds without relying on keyword matching.

4. Deterministic vs. Stochastic Software Design
   - Stochastic (LLM): Creative reasoning, natural language understanding, doc generation, refactoring ideas.
   - Deterministic (Python/Git/AST): File path validation, syntax compilation, diff generation,
     running pytest binaries, branch management.
   - Rule of Thumb: Never trust stochastic AI with system commands or file paths; always wrap AI in
     deterministic code guards.

SECTION 5: SECURITY BOUNDARIES & ZERO-TRUST EXECUTION POLICY
================================================================================

When interviewers ask "How did you handle security?", highlight these 7 pillars:

1. Public HTTPS Validation: Only `https://github.com/owner/repo` URLs are allowed. No SSH keys,
   no local file system paths.
2. Argument Array Git Execution: Git commands use list arguments `["git", "clone", ...]` rather
   than shell strings (`shell=False`) to prevent command injection.
3. Path Traversal Guard: Prevents `../` directory escapes. All read/write operations must stay
   strictly inside the temporary workspace folder.
4. Secret File Filtering: Ignores files containing `.env`, `credentials`, `secret`, `token`, `pem`,
   or `api_key`.
5. No Arbitrary Shell Execution: LLMs output JSON edit records (`file_path`, `start_line`,
   `new_content`), never terminal commands.
6. Fixed Test Allowlist: The test runner only executes pre-approved commands (`python -m pytest`)
   with subprocess timeouts, memory limits, and scrubbed environments.
7. BYOK (Bring Your Own Key) Privacy: Groq API keys passed by users are ephemeral, processed in
   memory, and never logged or written to disk.

SECTION 6: KEY TECHNICAL TRADE-OFFS & ENGINEERING DECISIONS
================================================================================

1. Local Embeddings (Sentence-Transformers) vs. OpenAI API Embeddings
   - Trade-off: Local CPU embeddings require memory (~90MB) and startup loading time.
   - Decision: Chosen to eliminate external per-call embedding API costs, ensure 100% privacy,
     and run without requiring cloud credentials for vector generation.

2. FAISS In-Memory Vector Index vs. Cloud Vector DB (Pinecone/Weaviate)
   - Trade-off: In-memory index is ephemeral and lost when server restarts or session expires.
   - Decision: Perfect for short-lived developer sessions analyzing dynamic repositories; avoids
     infrastructure overhead, setup latency, and cloud costs.

3. Render Free Tier Optimization (PyTorch CPU & Pre-warming)
   - Challenge: Render free tier has 512MB RAM limits and a 30-second HTTP proxy timeout. Downloading
     CUDA PyTorch (~800MB) causes build crashes, and first-time model loading causes 520/502 timeouts.
   - Solution: Used `--extra-index-url https://download.pytorch.org/whl/cpu` for a lightweight
     ~150MB PyTorch wheel, and added an `@app.on_event("startup")` handler in `api.py` to pre-warm the
     embedding model on boot.

SECTION 7: LIKELY INTERVIEW QUESTIONS & IMPRESSIVE MODEL ANSWERS
================================================================================

Q1: "Can you walk me through the architecture of RepoPilot?"
Answer:
"RepoPilot is a Python 3.12 and FastAPI platform that ingests public GitHub repos, indexes them using AST
symbol parsing and local FAISS vector embeddings, and provides a RAG-driven AI assistant for code QA,
architecture discovery, and automated code review.

What makes it unique is its Phase 10 controlled modification engine. Instead of allowing an LLM to execute
arbitrary shell commands, RepoPilot asks the LLM for structured edit records. It applies these edits inside an
isolated, disposable git clone, validates Python syntax using AST, runs allowlisted pytest commands under a
timeout, generates a real unified diff, and automatically rolls back if syntax or tests fail. Finally, approved
changes can be pushed as a Pull Request via GitHub's REST API."

Q2: "How do you prevent an LLM from hallucinating wrong code or deleting files?"
Answer:
"We enforce a strict separation between AI reasoning and system execution. The LLM is restricted to
returning structured JSON edit operations with explicit file paths and line ranges. Before any edit is applied,
our `WorkspaceTools` class checks for path traversal (`../`), sensitive file names (`.env`, secrets), and
workspace boundaries. After applying edits in a disposable workspace, our `ValidationService` runs
`ast.parse()` to guarantee syntax correctness. If syntax validation or pytest fails, the workspace is
automatically rolled back to its original state."

Q3: "Why did you choose FAISS and Sentence-Transformers over a managed vector database?"
Answer:
"Because repository analysis is ephemeral and session-based. When a developer analyzes a repo, we want
instant indexing without external infrastructure dependencies or cloud database costs. Local sentence-transformers
(`all-MiniLM-L6-v2`) generate 384D vectors in milliseconds, and `faiss-cpu` performs in-memory L2 search
sub-millisecond. It keeps the entire pipeline self-contained, private, and cost-free."

Q4: "What was the most challenging bug or performance bottleneck you solved during deployment?"
Answer:
"When deploying to cloud environments like Render's free tier (512MB RAM), we faced two major hurdles:
First, installing standard PyTorch pulled in CUDA GPU dependencies (~800MB), causing memory exhaustion. I
resolved this by configuring `pip` to pull PyTorch's CPU-only index wheel (~150MB). Second, downloading the
embedding model on the first HTTP request exceeded Render's 30-second proxy timeout, returning 502 Bad Gateway. I
implemented an `@app.on_event('startup')` pre-warming routine in `api.py` that pre-loads the model when the container
boots up, ensuring instant responses for end-users."

SECTION 8: TECHNICAL TERMINOLOGY GLOSSARY
================================================================================

- RAG (Retrieval-Augmented Generation): Injecting relevant retrieved context into LLM prompts.
- AST (Abstract Syntax Tree): Tree representation of source code structure created by a compiler/parser.
- Vector Embedding: Numerical vector representation capturing semantic meaning of text/code.
- FAISS: Facebook AI Similarity Search library for fast vector nearest-neighbor search.
- Ephemeral Workspace: Short-lived, temporary directory isolated per developer session.
- Unified Diff: Standard textual representation of changes between two versions of code files (`git diff`).
- Bring Your Own Key (BYOK): Design pattern where users supply their own API keys at runtime without storing them on the server.
- Grounded Answer: An AI response backed strictly by retrieved source evidence rather than unverified training memory.
